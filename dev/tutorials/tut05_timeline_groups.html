Timeline Groups

Commensurability, one shared start and end, exact linear conversion, timestamps from a group, and a child as a partial member

Timeline Groups

What you will build

You will put a Rachmaninoff score and performance into one , keeping the events loaded from both MIDI files as s on two s. Every member of a group shares one start and one end: score tick 0 is performance tick 0, and the score’s end is the performance’s end. For a score position between them, you will ask the group for the corresponding performance and see that the answer was interpolated.

Before you start

Complete Loading Real Data.

from fractions import Fraction

from timetoalign import (
    ContinuousLogicalTimeline,
    ContinuousPhysicalTimeline,
    Coordinate,
    IdCoordinate,
    PerformanceMidiLoader,
    ScoreMidiLoader,
    TimelineGroup,
    TimeUnit,
)
from timetoalign.testdata import ensure_data

midi_dir = ensure_data("midi")
score_path = midi_dir / "score" / "rachmaninoff_piano.mid"
performance_path = midi_dir / "performance" / "rachmaninoff_perf.mid"

The problem groups solve

Load the two files with the methods introduced in the previous tutorial. Each loader creates a complete timeline. Its is available through length, without inspecting loader metadata or MIDI-specific settings.

score_loader = ScoreMidiLoader.from_file(score_path)
performance_loader = PerformanceMidiLoader.from_file(performance_path)

score = score_loader.create_timeline(uid="rachmaninoff-score")
performance = performance_loader.create_timeline(uid="rachmaninoff-performance")
source_facts = {
    "score extent": score.length,
    "score events": score.n_events,
    "performance extent": performance.length,
    "performance events": performance.n_events,
}
source_facts
{'score extent': Coordinate(12473, ticks),
 'score events': 111,
 'performance extent': Coordinate(11537, ticks),
 'performance events': 111}

Both results contain the loaded musical events. Their extents are native MIDI ticks: ticks in a quantized score and ticks in a performance are separate coordinate systems even though they share a unit name, so a value on one is not automatically a value on the other.

Building a group

Create an empty group, then add the two loaded timelines. Membership declares their : by definition, every member’s 0 coincides with every other member’s 0 and every member’s length with every other member’s length, so the group relates any position on one member to a position on the other.

group = TimelineGroup(id="rachmaninoff-score-performance")
group.add_timeline(score)
group.add_timeline(performance)

retrieved_score = group.get_timeline(score.id)
members_present = all(
    timeline_id in group.timeline_ids for timeline_id in (score.id, performance.id)
)
group_facts = {
    "are_commensurable": members_present,
    "n_timelines": group.n_timelines,
    "timeline_ids": group.timeline_ids,
    "retrieved timeline": retrieved_score.id,
}
group_facts
{'are_commensurable': True,
 'n_timelines': 2,
 'timeline_ids': ['rachmaninoff-score', 'rachmaninoff-performance'],
 'retrieved timeline': 'rachmaninoff-score'}

Both IDs are present, n_timelines is two, and get_timeline returns the score by ID. The are_commensurable label reports the consequence of that membership; the method with that name belongs to the bundle API introduced in the next tutorial.

Between the start and the end

A position between the shared start and end converts linearly: position p on one member is p · len_B / len_A on the other, computed exactly and then written the way the target member writes numbers. get_coordinate_at applies it: name the source axis by wrapping the value in an IdCoordinate, and name the axis you want the answer on with timeline_id. This linear interpolation is the second of three coordinate-transfer mechanisms in the series, after the exact parent/child offsets introduced in Nesting and Timestamps.

assert group_facts["are_commensurable"]
assert score.n_events == source_facts["score events"]

score_position = Coordinate(6000, TimeUnit.ticks)
performance_position = group.get_coordinate_at(
    IdCoordinate(score_position.value, score_position.unit, score.id),
    timeline_id=performance.id,
)
map_example = {
    "score length": score.length,
    "performance length": performance.length,
    "score coordinate": score_position,
    "performance coordinate": performance_position,
}
map_example
{'score length': Coordinate(12473, ticks),
 'performance length': Coordinate(11537, ticks),
 'score coordinate': Coordinate(6000, ticks),
 'performance coordinate': IdCoordinate(5550, ticks, 'rachmaninoff-performance')}

The answer comes back as an IdCoordinate, not a bare number, so the target unit, the integer required by the performance timeline, and the timeline the value belongs to all remain visible. The ratio of the two lengths is the whole relation: one constant ratio cannot represent rubato, fermatas, or other local timing differences.

Transferring one coordinate

get_timestamp_at returns a across the group. Its coordinate accessors expose the queried position and the corresponding position on the other member.

shared_stamp = group.get_timestamp_at(score_position, score.id)
stamp_view = {
    "score coordinate": shared_stamp.get_coordinate(score.id),
    "performance coordinate": shared_stamp.get_coordinate(performance.id),
    "is_interpolated": shared_stamp.is_interpolated,
}
assert stamp_view["performance coordinate"] == map_example["performance coordinate"]
stamp_view
{'score coordinate': IdCoordinate(6000, ticks, 'rachmaninoff-score'),
 'performance coordinate': IdCoordinate(5550, ticks, 'rachmaninoff-performance'),
 'is_interpolated': True}

Both values are unit-bearing coordinates. is_interpolated is true because score tick 6000 lies between the shared start and end rather than on one of them; the flag describes how the answer was obtained, not how accurately two endpoints model expressive timing. The group answers with the same TimeStamp type a single timeline returns, so everything you learned about stamps in Nesting and Timestamps applies unchanged.

Transferring several coordinates

Retrieval follows one grid, and a batch is where you can see the whole of it. The suffix names what you are asking with: _at takes a position, _for takes a key such as an event ID. The plural of the noun takes many of them. The bare name — get_timestamp(...) — is a convenience dispatcher that picks the precise method from what you hand it, and the table is that same query asked for in tabular form.

So get_timestamps_at is simply the plural of get_timestamp_at: the same transfer, many positions. Use integer tick positions because ticks are a discrete unit.

batch_positions = [
    Coordinate(0, TimeUnit.ticks),
    Coordinate(4000, TimeUnit.ticks),
    Coordinate(8000, TimeUnit.ticks),
]
batch_stamps = group.get_timestamps_at(
    batch_positions,
    score.id,
)
batch_stamps
[TimeStamp(axis=0 ticks @rachmaninoff-score, source='rachmaninoff-score'),
 TimeStamp(axis=4000 ticks @rachmaninoff-score, source='rachmaninoff-score' (interpolated)),
 TimeStamp(axis=8000 ticks @rachmaninoff-score, source='rachmaninoff-score' (interpolated))]

You get one TimeStamp per requested position, in the order you asked for them. A plural getter always returns a list of stamps and never collapses them into a table — tabulating is a separate question, asked of get_timestamp_table with the same arguments.

batch_frame = group.get_timestamp_table(
    batch_positions,
    score.id,
    format="dataframe",
)
batch_frame
rachmaninoff-score (ticks) rachmaninoff-performance (ticks)
0 0 0
1 4000 3700
2 8000 7400

Each input score tick now appears beside its mapped performance tick. Every column names the member it belongs to, and every cell holds one value in that member’s declared number type — integers here, because both axes are ticks. The default format="table" answers the same query as a PyArrow table whose cells are coordinate structs instead.

The shared start

At the shared start, every member stands at 0. A stamp asked for there is not interpolated: the start and the end are the two positions the group stores.

start_stamp = group.get_timestamp_at(Coordinate(0, TimeUnit.ticks), score.id)
start_view = {
    score.id: start_stamp.get_coordinate(score.id),
    performance.id: start_stamp.get_coordinate(performance.id),
    "is_interpolated": start_stamp.is_interpolated,
}
start_view
{'rachmaninoff-score': IdCoordinate(0, ticks, 'rachmaninoff-score'),
 'rachmaninoff-performance': IdCoordinate(0, ticks, 'rachmaninoff-performance'),
 'is_interpolated': False}

The mapping displays both unit-bearing coordinates at the start and shows is_interpolated as false.

The whole table

Asked without a position, get_timestamp_table materializes the stored rows at once: the shared start and the shared end, each member at 0 and at its own length.

assert start_view["is_interpolated"] is False
assert len(batch_frame) == 3
group_frame = group.get_timestamp_table(format="dataframe", units=True)
group_frame
rachmaninoff-score (ticks) rachmaninoff-performance (ticks)
0 0 0
1 12473 11537

The two rows are the shared start and end; the three-row batch above contained requested positions, not three stored rows. The tick columns hold integers, because ticks are a unit and a column is re-expressed in its axis’s declared type just as a scalar accessor is. The columnar view and the scalar accessors agree; neither is a lower-fidelity shortcut to the other.

The represented range

get_interval_for reports a member’s range in the group. Every member spans the whole group, so the range is the member’s own axis from 0 to its length.

score_range = group.get_interval_for(score.id)
range_view = {
    "reported range": score_range,
    "range duration": score_range.duration,
    "timeline extent": retrieved_score.length,
}
range_view
{'reported range': Interval(start=Coordinate(0, ticks), end=Coordinate(12473, ticks)),
 'range duration': Duration(12473, ticks),
 'timeline extent': Coordinate(12473, ticks)}

The range runs from zero to the endpoint carried by the score’s unit-bearing length. get_interval_for returns one rather than a pair of numbers, so both endpoints keep the tick unit and the integer representation a axis requires, and the span’s own duration is available without subtracting anything by hand. Asking for a member the group does not hold raises KeyError; absence is reported, never returned as an empty value.

Partial alignment

A member always spans the whole group, so when a recording covers only part of a score, the part is what joins the group: a child of the score, which carries the part’s exact offset. In this small, deliberately constructed example, a 40-second recording covers only score quarters 8 through 16.

partial_score = ContinuousLogicalTimeline.from_events(
    [{"id": "score-end", "event_type": "Boundary", "instant": Fraction(16)}],
    uid="sixteen-quarter-score",
)
second_half = partial_score.create_child(
    length=Fraction(8), offset=Fraction(8), uid="second-half"
)
second_half_recording = ContinuousPhysicalTimeline.from_events(
    [{"id": "recording-end", "event_type": "Boundary", "instant": 40.0}],
    uid="second-half-recording",
)
partial_group = TimelineGroup(
    id="second-half-only", timelines=[second_half, second_half_recording]
)
partial_group.timeline_ids
['second-half', 'second-half-recording']

The group holds the second half and the recording; the score itself is no member. A score position reaches the recording in two steps, each a mechanism you already know: the exact offset carries it onto the child, and the group carries the child’s position onto the recording.

second_half_boundary = Coordinate(Fraction(8), TimeUnit.quarters)
between_pairs = Coordinate(Fraction(25, 2), TimeUnit.quarters)


def recording_position(score_position: Coordinate) -> dict:
    """Carry a score position onto the child, then across the group."""
    on_child = partial_score.get_timestamp_at(score_position).get_coordinate(
        second_half.id
    )
    stamp = partial_group.get_timestamp_at(on_child)
    return {
        "on the child": on_child,
        "on the recording": stamp.get_coordinate(second_half_recording.id),
        "is_interpolated": stamp.is_interpolated,
    }


partial_checks = {
    "quarter 8": recording_position(second_half_boundary),
    "quarter 25/2": recording_position(between_pairs),
}
partial_checks
{'quarter 8': {'on the child': IdCoordinate(Fraction(0, 1), quarters, 'second-half'),
  'on the recording': IdCoordinate(0.0, seconds, 'second-half-recording'),
  'is_interpolated': False},
 'quarter 25/2': {'on the child': IdCoordinate(Fraction(9, 2), quarters, 'second-half'),
  'on the recording': IdCoordinate(22.5, seconds, 'second-half-recording'),
  'is_interpolated': True}}

Quarter 8 is the child’s 0, the shared start of the group, and maps to 0 seconds, so its flag is false. Quarter 25/2 is the child’s exact 9/2, which maps to 22.5 seconds and has a true interpolation flag. With no further stored positions, the group cannot measure how far this straight-line estimate departs from the performed rubato.

What you learned

  • You can load event-bearing score and performance timelines and compare their extents.
  • You can build a group, inspect its members, and establish commensurability.
  • You can use the group’s linear conversion through get_coordinate_at.
  • You can transfer one coordinate and identify an interpolated answer.
  • You can transfer a batch of discrete coordinates and tabulate the same query.
  • You can read the shared start as a stamp that is not interpolated.
  • You can inspect the stored start and end rows and read one typed value per cell.
  • You can query a member’s represented range.
  • You can align a recording to only part of a score by grouping it with a child.
